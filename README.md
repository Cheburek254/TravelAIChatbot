# TravelAIChatbot

**От одного сообщения — к двум вариантам поездки с понятной полной стоимостью.**

ИИ-помощник уточняет пожелания, ищет отели и транспорт и помогает выбрать путешествие. Чат расположен рядом с карточками поездки, сравнением, маршрутом и демонстрационным оформлением.

[Развёртывание на сервере](DEPLOY.md)

> **Интерактивный MVP интеллектуального турагента:** умный подбор направлений, стыковка авиарейсов через API Яндекс Расписаний, прогноз погоды Open-Meteo и прозрачный расчёт полной стоимости поездки.

**Навигация:** [Запуск с Docker](#запуск-с-docker) · [Своя модель ИИ](#своя-модель-ии) · [Своя БД и каталог](#своя-база-данных-и-свой-каталог) · [Расписания Яндекса](#расписания-и-маршруты-с-пересадками) · [Архитектура](#как-это-работает) · [Тесты](#проверки-и-бенчмарк) · [История изменений](#история-изменений)

## Что умеет приложение

| Возможность | Как работает |
| --- | --- |
| Поездка с нуля | Новый чат открывает подсказку; сохранённая поездка восстанавливается из SQL |
| Варианты А и Б | Карточки отеля, транспорта, условий, полной сметы и таймлайна |
| Обсуждение поездки | Вопросы об отеле, питании, отмене и сохранённой смете не пересобирают карточки |
| Строгий бюджет | Сервер учитывает обязательные доплаты и возвратный депозит; дорогие варианты не попадают в карточки |
| Диапазон «от–до» | Бюджет задаётся в чате: «бюджет от 80 до 150 тыс.» или «минимум 80 тыс.»; цены не увеличиваются искусственно |
| Самая дешёвая поездка | Кнопка выбирает минимум под сохранённые условия: внутри выбранного направления или по всему каталогу, если направление ещё не задано |
| Другие направления | До трёх альтернатив из каталога с сохранением бюджета и условий, без повторения текущего направления |
| Тип отдыха | «Хочу в горы» и «Хочу к морю» заново предлагают направления; пожелание сохраняется для альтернатив и поиска минимальной стоимости |
| Условный перенос дат | Календарь сдвигает поездку, сохраняя число ночей и все суммы; оценка погоды обновляется |
| Гости и питомцы | Даты и число гостей редактируются нажатием на поля в шапке. Гости пересчитывают смету; плашка Pet-friendly появляется только при поездке с питомцем |
| Бонусные баллы | При наведении, фокусе или нажатии открывается окошко с расчётом: 1,5%, минимум 150 баллов; начисление демонстрационное |
| Контекстные кнопки | Подсказки зависят от этапа; стандартные действия выполняются без обращения к модели |
| Независимые чаты | Свой `session_id` для каждой вкладки, история и состояние хранятся в базе |
| Резервные модели | OpenRouter и необязательный независимый резерв Groq с ограниченным временем ожидания |

## Запуск с Docker

Нужны **Git, Docker и Docker Compose v2.24+**. Python и Node.js для этого способа не требуются. Команды выполняются из корня репозитория; используйте корневой `docker-compose.yml`.

### 1. Получить проект и создать настройки

```bash
git clone https://github.com/Cheburek254/TravelAIChatbot.git
cd TravelAIChatbot
```

Linux / macOS:

```bash
cp .env.defaults .env
```

Windows PowerShell:

```powershell
Copy-Item .env.defaults .env
```

Откройте **`.env` в корне проекта**. Для диалога с настоящей моделью заполните `OPENROUTER_API_KEY` или `GROQ_API_KEY` по [инструкции ниже](#своя-модель-ии). В режиме без внешних API-ключей автоматически включается локальный детерминированный Mock AI, позволяющий проверить весь UX и бизнес-логику без расхода токенов. `.env.example` содержит только имена переменных с пустыми значениями; рабочие несекретные значения вынесены в `.env.defaults`.

### 2. Запустить приложение и PostgreSQL

```bash
docker compose config --quiet
docker compose up --build -d
docker compose ps
```

Оба сервиса, `app` и `db`, должны перейти в состояние **healthy**. При первом запуске Docker скачает образы, установит зависимости и соберёт фронтенд.

| Адрес | Назначение |
| --- | --- |
| [localhost:8080](http://localhost:8080/) | Приложение |
| [localhost:8080/health](http://localhost:8080/health) | Проверка доступности: `{"status":"ok"}` |
| [localhost:8080/docs](http://localhost:8080/docs) | Swagger UI и схемы API |
| [localhost:8080/tools-dashboard](http://localhost:8080/tools-dashboard) | Проверка инструментов поиска |

Если порт занят, задайте в `.env` `APP_PUBLIC_PORT=18080` и повторите запуск; приложение будет доступно на `http://localhost:18080`.

### 3. Остановка и обновление

```bash
docker compose stop
# После изменения исходников:
docker compose up --build -d
```

Каталог и история остаются в томе `postgres_data`. Обычный `docker compose down` тоже сохраняет данные; флаг **`-v` удаляет базу**. Полная инструкция для общего сервера, reverse proxy и резервных копий — в [DEPLOY.md](DEPLOY.md).

## Своя модель ИИ

Все настройки находятся в **корневом `.env`**, ключи читает только backend. Переменные `VITE_*` для секретов не нужны. В примерах значения в угловых скобках замените своими.

### Вариант А · модель через OpenRouter

```dotenv
OPENROUTER_API_KEY=<ваш_ключ_OpenRouter>
OPENROUTER_BASE_URL=https://openrouter.ai/api/v1
OPENROUTER_MODEL=<точный_ID_модели_из_OpenRouter>
OPENROUTER_FALLBACK_MODELS=
GROQ_API_KEY=
```

Модель должна поддерживать **Chat Completions и tool calling / function calling**: агент передаёт JSON-схемы инструментов и обрабатывает `tool_calls`. Одного текстового ответа недостаточно для полного сценария.

В [.env.defaults](.env.defaults) основная модель — **`google/gemini-3.5-flash-lite`**. Резерв: `google/gemini-2.0-flash-001`, `google/gemma-4-31b-it:free`, `google/gemma-4-26b-a4b-it:free`, `nvidia/nemotron-3.5-lightning:free`, `openrouter/free`. Доступность моделей и квоты определяются провайдером и аккаунтом. Если платная модель отклонена с HTTP 402, сервер пробует бесплатные модели, в том числе из той же группы, и независимый Groq, если он настроен.

Для проверки именно своей модели оставьте `OPENROUTER_FALLBACK_MODELS=` пустым и отключите Groq, как в примере. Чтобы разрешить резерв, перечислите точные ID через запятую. **Если основная модель бесплатная (`:free` или `openrouter/free`), код разрешает только бесплатный резерв OpenRouter.** Для платной модели используйте её ID и ключ аккаунта с соответствующим доступом.

### Вариант Б · модель через Groq

```dotenv
OPENROUTER_API_KEY=
GROQ_API_KEY=<ваш_ключ_Groq>
GROQ_BASE_URL=https://api.groq.com/openai/v1
GROQ_MODEL=<точный_ID_модели_из_Groq>
GROQ_FALLBACK_MODELS=
```

Приложение работает с одним ключом Groq. Чтобы использовать Groq как независимый резерв, заполните **оба** ключа и задайте `GROQ_FALLBACK_MODELS` через запятую. Примеры моделей есть в [.env.defaults](.env.defaults); отдельный ключ OpenAI для моделей, вызываемых через Groq, не требуется.

### Вариант В · собственный сервер модели

Для собственного API можно использовать настраиваемую ветку Groq, заменив базовый URL:

```dotenv
OPENROUTER_API_KEY=
GROQ_API_KEY=<токен_вашего_API>
GROQ_BASE_URL=https://your-model.example/v1
GROQ_MODEL=<ID_вашей_модели>
GROQ_FALLBACK_MODELS=
```

Приложение добавляет `/chat/completions` к базовому URL и отправляет `Authorization: Bearer …`. Endpoint должен быть доступен **из контейнера**, поддерживать формат Chat Completions, JSON-схемы инструментов, `tool_choice`, `max_tokens` и `parallel_tool_calls: false`. Шлюз [llm_gateway.py](<data tools/src/services/llm_gateway.py>) поддерживает любые OpenAI-совместимые API (vLLM, Ollama, LocalAI, Groq). Базовый URL и токен настраиваются через переменные окружения.

Если модель запущена на том же компьютере, `localhost` внутри контейнера указывает на приложение. В Docker Desktop для доступа к хосту обычно используют `host.docker.internal`; на Linux доступ к хосту настраивается отдельно.

### Применить настройки и проверить

После **любого изменения ключа, URL или модели**:

```bash
docker compose up -d --force-recreate app
```

Окружение уже созданного контейнера обновляется при его пересоздании. При запуске без Docker остановите и снова запустите Python backend.

Отправьте сообщение в новом чате. В ответе `/api/chat` поле `models_used` показывает фактически использованные модели, включая резерв. Его можно посмотреть в браузере: **DevTools → Network → `/api/chat` → Response**. При исчерпании квот или отказе всех провайдеров чат показывает ошибку и сохраняет предыдущую историю и план.
## Как это работает

```text
React: чат, карточки, сравнение, календарь, оформление
                         │ JSON /api/*
                         ▼
FastAPI: сессии, ограничения, серверные действия и оркестратор
          │                       │                     │
          ▼                       ▼                     ▼
     PostgreSQL           OpenRouter / Groq        Open-Meteo
   каталог + история       вызовы инструментов    прогноз / климат
```

**Модель понимает запрос, сервер проверяет результат.** Поиск направлений, отелей, перелётов/трансферов и погоды доступен через инструменты. `build_trip_plan` собирает карточки и смету; модель не назначает произвольную итоговую цену. Сервер учитывает транспорт, проживание, обязательные сборы и депозит, проверяет логистику и сохраняет пользовательский лимит бюджета.

**Меньше данных и обращений к LLM.** Отели фильтруются и сортируются SQL-запросом по направлению, цене и условиям; смысловой поиск работает с ограниченной подборкой. В контекст попадают до трёх направлений и пяти отелей, без фотографий и всех месяцев климата. Старые ходы истории сокращаются целиком. Сравнение, выбор варианта, стандартные изменения питания, альтернативы и перенос дат выполняются без LLM. Условный перенос дат сохраняет ранее рассчитанную смету; изменение других условий требует нового расчёта.

**Устойчивость чата.** OpenRouter перебирается группами максимум по три модели; доступен независимый резерв Groq и ограничение времени ожидания. Явно повреждённые, пустые и обрезанные ответы отбраковываются; повреждённые сообщения ассистента в сохранённой истории заменяются заметкой. Многоуровневая валидация схем инструментов (JSON Schema) и санитайзинг контекста минимизируют риск галлюцинаций модели.

**Изоляция сессий.** UUID хранится в `sessionStorage` вкладки. В SQL сохраняются последние 20 сообщений, условия, варианты и выбор пользователя. Запросы одной сессии сериализуются; текущий запуск рассчитан на один процесс приложения. Несколько экземпляров backend потребуют общей синхронизации.

## Своя база данных и свой каталог

Приложение работает через SQLAlchemy 2.x ([database.py](<data tools/src/services/database.py>)) и поддерживает как **PostgreSQL**, так и **SQLite**. При старте автоматически создаются таблицы `destinations`, `hotels`, `routes` и `chat_sessions`, после чего недостающие записи по `id` заполняются из JSON-каталога ([`data tools/data/`](<data tools/data>)), не перезаписывая уже существующие строки в базе.

### 1. Подключение своей внешней PostgreSQL или SQLite
Укажите строку подключения в переменной `DATABASE_URL` в корневом `.env`:

```dotenv
# Внешняя PostgreSQL:
DATABASE_URL=postgresql+psycopg://user:password@your-db-host:5432/dbname

# Или файл SQLite (при локальном запуске без Docker создаётся автоматически как data tools/travel.db):
DATABASE_URL=sqlite:///./custom_travel.db
```

В [`docker-compose.yml`](docker-compose.yml) переменная `DATABASE_URL` из `.env` имеет приоритет над встроенным контейнером `db`. После изменения `.env` пересоздайте контейнер приложения:

```bash
docker compose up -d --force-recreate app
```

### 2. Редактирование каталога напрямую в SQL или через JSON
Вы можете подключиться к работающей PostgreSQL и изменить цены, отели или добавить свои записи:

```bash
docker compose exec db psql -U travel -d travel
```

```sql
SELECT id, name, price_per_night FROM hotels;
UPDATE hotels SET price_per_night = 12000 WHERE id = 'hotel_gesh_01';
```

После изменения попросите чат пересобрать поездку — новый поиск сразу прочитает обновлённые данные из SQL (сохранённая карточка до пересборки остаётся снимком предыдущего расчёта). Чтобы загрузить полностью собственный каталог с нуля, замените или дополните [`destinations.json`](<data tools/data/destinations.json>), [`hotels.json`](<data tools/data/hotels.json>) и [`transfers.json`](<data tools/data/transfers.json>) перед первым запуском (или пересоздайте том базы `docker compose down -v && docker compose up --build -d`).

## Настройки и диагностика

| Переменная | Назначение |
| --- | --- |
| `APP_PUBLIC_PORT` / `APP_BIND_ADDRESS` | Внешний порт и адрес Docker; по умолчанию `8080` / `0.0.0.0` |
| `APP_PORT` / `APP_HOST` | Порт и адрес Python без Docker; Compose фиксирует внутренний порт `8080` |
| `POSTGRES_PASSWORD` | Пароль базы; шаблон содержит локальный демопароль, для сервера задайте свой из букв и цифр |
| `DATABASE_URL` | Строка подключения к своей PostgreSQL/SQLite; если не задана в `.env`, Compose подключает встроенный контейнер PostgreSQL, а локальный Python использует SQLite `travel.db` |
| `WEATHER_TIMEOUT_SECONDS` | Ожидание сервиса погоды, по умолчанию `4.0` секунды |
| `OPENROUTER_*` / `GROQ_*` | Ключ, основной ID, базовый URL и резервные модели; [примеры настройки выше](#своя-модель-ии) |
| `YANDEX_RASP_ENABLED` | Флаг использования API Яндекс Расписаний: `true` (по умолчанию) — живой поиск при наличии ключей; `false` — принудительно использовать мок-данные из каталога |
| `YANDEX_RASP_API_KEYS` | Один или несколько ключей Яндекс Расписаний через запятую |

Для контейнеров заданы лимиты 512 МБ для приложения и 256 МБ для PostgreSQL; сборка требует дополнительных ресурсов. Доступ в интернет нужен для загрузки зависимостей, модели и прогноза.

```bash
docker compose ps
docker compose logs --tail=100 app db
```

| Симптом | Что проверить |
| --- | --- |
| Работает только деморежим | Ключ задан в корневом `.env`, контейнер `app` пересоздан |
| Ошибка ИИ / HTTP 400 | Модель поддерживает инструменты, URL и ID верны; попробуйте совместимую резервную модель |
| HTTP 401 / 403 / 429 | Ключ, доступ к модели и лимиты аккаунта у соответствующего провайдера |
| После изменения `.env` модель прежняя | Выполните `docker compose up -d --force-recreate app` |
| Порт 8080 занят | Измените `APP_PUBLIC_PORT`, затем повторите запуск |
| После обновления база выглядит пустой | Проверьте, что имя Compose-проекта и постоянный том остались прежними |

## Локальная разработка без Docker

Используемые в Docker версии — **Python 3.12 и Node.js 22**. Создайте корневой `.env` по инструкции выше. Без `DATABASE_URL` backend сам создаст локальную SQLite; для этого способа PostgreSQL не требуется.

### После свежего клонирования: установка зависимостей

Git не переносит `.venv` и `node_modules`: каждый участник устанавливает зависимости у себя. Все команды ниже выполняются **из корня репозитория**. Для тестов API-ключи и работающий сервер не нужны.

**Windows PowerShell** — активация окружения не требуется:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r ".\data tools\requirements.txt"
npm --prefix frontend ci
.\.venv\Scripts\python.exe scripts/checks.py
```

Если установлено несколько версий Python, создайте окружение командой `py -3.12 -m venv .venv`. После установки запускайте проверки через `.\.venv\Scripts\python.exe`, чтобы использовать именно это окружение.

**Linux / macOS:**

```bash
python3 -m venv .venv
./.venv/bin/python -m pip install -r "data tools/requirements.txt"
npm --prefix frontend ci
./.venv/bin/python scripts/checks.py
```

Ошибки `No module named 'sqlalchemy'` / `No module named 'httpx'` означают, что пакеты не установлены в используемый Python. Повторите установку через тот же интерпретатор из `.venv`. Скрипт проверок заранее проверяет зависимости и показывает команды установки. Для отдельной проверки backend используйте `scripts/checks.py --backend-only`, frontend — `--frontend-only`.

### Запуск приложения

```bash
python -m venv .venv
```

Активируйте окружение: Linux / macOS — `source .venv/bin/activate`; Windows PowerShell — `.venv\Scripts\Activate.ps1`.

```bash
python -m pip install -r "data tools/requirements.txt"
python "data tools/main.py"
# При необходимости принудительно отключить Яндекс API (использовать мок-данные):
python "data tools/main.py" --yandex-rasp false
```

В другом терминале из корня проекта:

```bash
cd frontend
npm ci
npm run dev
```

Откройте [localhost:5173](http://localhost:5173/). Vite проксирует `/api` и `/health` на `127.0.0.1:8080`; при изменении порта backend обновите [vite.config.js](frontend/vite.config.js). Для Swagger используйте адрес backend `http://localhost:8080/docs`.

## Взрослые, дети и город вылета

В шапке и быстрых действиях доступны «Взрослые и дети» и «Город вылета». Укажите возраст каждого ребёнка **на день вылета**. Нужен хотя бы один взрослый; всего до 10 гостей. Для каждого младенца до 2 лет нужен сопровождающий взрослый. Состав группы и возраст сохраняются в SQL-сессии и ваучере.

Демонстрационные правила расчёта:

| Статья | Правило |
| --- | --- |
| Перелёт | Взрослый и ребёнок 12–17 лет — 100%; 2–11 лет — 75%; до 2 лет — 10% без отдельного места |
| Багаж | Доплата при безбагажном тарифе только за пассажиров с местом |
| Отель | Стандартный номер на 2 места; число номеров округляется вверх, младенец без отдельного места. Для младенцев выбираются отели с бесплатной доступной кроваткой |
| Питание, если добавлено | 2600 ₽ на взрослого и 1300 ₽ на ребёнка от 2 лет за поездку; до 2 лет без доплаты |
| Курортный сбор | По ставке демонстрационного каталога только за взрослых |
| Трансфер | Вместимость для всей группы; для детей до 7 лет нужен вариант с детским креслом |

Это **демотарифы приложения**, не реальные правила конкретной авиакомпании или отеля. Цены расписаний Яндекса не используются как стоимость покупки. Смена состава или города пересчитывает полную смету вместе с обязательными доплатами и депозитом. Если предложение не входит в бюджет, текущий план сохраняется; бюджет меняется только в чате.

## Расписания и маршруты с пересадками

Если нужны живые расписания, задайте в `.env`:

```dotenv
YANDEX_RASP_ENABLED=true
YANDEX_RASP_API_KEYS=
```

Впишите один ключ или несколько через запятую (поддерживается также `YANDEX_RASP_API_KEY` для одного ключа). По умолчанию `YANDEX_RASP_ENABLED=true`: при наличии ключей приложение запрашивает живое расписание Яндекса. Если выставить `YANDEX_RASP_ENABLED=false` в `.env` (или запустить локальный сервер с флагом `python "data tools/main.py" --yandex-rasp false` / `--no-yandex-rasp`), запросы к Яндекс API отключаются и сразу используются мок-данные расписаний из каталога (при этом прогноз погоды Open-Meteo продолжает работать). Для полного отключения всех внешних запросов расписаний и погоды используйте `OFFLINE_MODE=1`; ключи ИИ управляются отдельно.

Интеграция использует [официальный API Яндекс Расписаний](https://yandex.ru/dev/rasp/doc/ru/reference/schedule-point-point) на `api.rasp.yandex-net.ru`. Ключ передаётся в заголовке; каждый резервный ключ проверяется максимум один раз за попытку. Расписание загружается с пагинацией и кешируется на 10 минут.

Маршруты А → Б могут состоять из нескольких участков. Сервер проверяет порядок отправления и прибытия в абсолютном времени с часовыми поясами, станции пересадки, наличие переезда между разными станциями, длительность ожидания и обратный маршрут. Минимальные запасы в демопланировщике: 90 минут при авиапересадке в одной станции и 180 минут при смене аэропорта; для наземных участков 15/60 минут. Неизвестные или непроверяемые участки не выдаются как подтверждённый маршрут. Среди подходящих по бюджету вариантов предпочитается прямой авиарейс; если он не подходит, допустимы пересадки, в том числе смешанный транспорт. Кнопка «Самая дешёвая поездка» по-прежнему выбирает минимальную полную стоимость.

Участки, пересадки, местные времена и часовые пояса показываются в карточке и маршруте. Переезд между станциями учитывается отдельным демотарифом 1500 ₽ за переезд. Успешный пустой ответ Яндекса означает отсутствие подходящих рейсов, а не разрешение выдумать их. При недоступности провайдера включается явно подписанное демонстрационное расписание целиком, без смешивания настоящего вылета с выдуманным возвратом.

В редакторе дат изменение длительности или времени вылета запускает проверку и пересчёт; невозможное время не применяется. Условный перенос тех же ночей без изменения времени сохраняет цены и обновляет погоду; он явно помечается как условный перенос расписания.


Чат различает время отправления и прибытия: «прилёт до 12.30» ограничивает прибытие в пункт назначения в день заезда, «вернуться до обеда» — прибытие домой до 12:00, а «обратный вылет до обеда» — отправление обратного рейса. Поддерживаются часы через точку и двоеточие. Новое пожелание заменяет прежние ограничения времени для соответствующего направления. При отсутствии билетов сохраняется прежний план с явным сообщением об отказе.

«Выведи другие отели» исключает текущие отели из нового поиска с сохранением бюджета и условий. Если новых подходящих отелей нет, карточки сохраняются и чат сообщает причину. Список городов вылета в чате совпадает со списком в шапке; неподдерживаемый город не заменяется без выбора пользователя.


### Разговорный чат и уточнения

Общие сокращения раскрываются до разбора: `2взр + реб8`, `4н`, «до сотки», «300 штук», СПБ/МСК/Екб/Нск/НН/Минводы. Исходное сообщение остаётся в истории. Короткое «а попозже?» учитывает последнюю тему перелёта; без понятного контекста бот уточняет пожелание. «Вчетвером» означает общее число гостей, включая детей; при неизвестном возрасте бот сохраняет город, даты и бюджет до ответа.

Модель может сама перевести разговорное пожелание в параметры поиска и объяснить трактовку. Для нестандартного изменения она передаёт точную цитату запроса и пояснение; сервер валидирует параметры, считает полную стоимость и применяет только доступное изменение. Бюджет не повышается по решению модели, возраст детей не угадывается. Обсуждение поездки не меняет карточки. При отказе доступны конкретная причина и варианты изменения условий; уточняющий вопрос «что поменять?» использует последний результат поиска.

«Оформи ранний заезд» добавляет услугу только для отеля, допускающего её, и рейса с ранним прибытием. Демодоплата — 50% стоимости ночи всех номеров с округлением до 100 ₽; она входит в лимит бюджета, таймлайн и чек. «Убери ранний заезд» отменяет услугу. Это демонстрационный расчёт, не запрос реального бронирования. Дата оформления ваучера явно указывается по Москве (UTC+03:00).

### Номера и пересчёт стоимости

Длительность маршрута показывается в часах и минутах. Чат принимает «хочу 3 номера» или «можно 2 номера вместо 3»: число номеров обновляется в карточках и полной смете, включая ранний заезд. Демотариф предусматривает два места в номере; дети с 2 лет занимают место. Если номеров недостаточно или пересчёт превышает бюджет, чат объясняет причину и сохраняет прежний план. Самостоятельно уменьшать состав гостей модель не может.
